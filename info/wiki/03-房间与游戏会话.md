# 03 房间与游戏会话

更新时间：2026-07-13

## GameModule

`GameModule` 描述一种玩法，不保存单局运行状态：

```kotlin
interface GameModule {
    val id: String
    val displayName: String
    val minPlayers: Int
    val maxPlayers: Int

    fun defaultDefinition(): GameDefinition
    fun spectatorPolicy(room: GameRoom): SpectatorPolicy
    fun canSpectate(room: GameRoom, player: Player): Boolean
    fun createSession(room: GameRoom): GameSession
}
```

`GameDefinition` 可声明：

- 启用状态和描述。
- 最小/最大人数。
- 默认时长、准备和倒计时。
- 公共地图模板。
- required/optional Bukkit 插件。
- 资源包。
- 观战策略。

`canSpectate(room, player)` 默认返回 `true`，用于在通用 `SpectatorPolicy` 之前增加玩法和玩家相关的准入判断，例如地图开关、权限或白名单；返回 `false` 时主插件不会修改玩家快照、房间集合或观战状态。

## GameRoom

房间包含：

- 四位 `id`。
- `module` 和实际 `definition`。
- 可选 `configuredGame` 托管游戏。
- `mapTemplate` 和 `templateDirectory`。
- 房间名称和房主。
- 玩家/观战者 UUID 集合。
- 当前 `GameState`、世界和 session。

不要把 GameRoom 长期保存在静态字段中；房间关闭后对象不再有效。

## GameSession 生命周期

```kotlin
interface GameSession {
    val room: GameRoom
    fun onPrepare()
    fun onPlayerJoin(player: Player)
    fun onPlayerLeave(player: Player)
    fun onSpectatorJoin(player: Player)
    fun onSpectatorLeave(player: Player)
    fun onPlayerDeath(player: Player)
    fun onPlayerKill(killer: Player, victim: Player)
    fun resolveKiller(victim: Player): Player?
    fun reconnectGraceTicks(player: Player): Long
    fun onPlayerDisconnect(player: Player)
    fun onPlayerReconnect(player: Player)
    fun onPlayerReconnectExpired(playerId: UUID)
    fun routeChat(player: Player, message: String, requestedChannel: GameChatChannel): GameChatRoute?
    fun usesCustomScoreboard(): Boolean
    fun usesCustomActionBar(): Boolean
    fun onStart()
    fun onTick()
    fun onEnd()
    fun onClose()
}
```

`routeChat` 默认原样返回请求频道与文本，因此旧模块无需修改。玩法可返回新的 `GameChatRoute` 改写频道、文本、格式 `variant` 或显式受众；显式受众会被主插件限制在当前房间，返回 `null` 表示玩法已拒绝并自行提示该消息。路由回调抛异常时核心记录警告并抑制该条消息，不回退到可能扩大受众的默认频道；回调期间玩家离房或房间关闭时同样停止发送。

### onPrepare

- 只执行一次房间准备。
- 创建临时世界并写入 `room.world`。
- 加载托管游戏配置。
- 初始化房间级静态资源。
- 创建失败时保持 `room.world == null`，主插件会把房间恢复到 CREATED。

`CREATED -> PREPARING` 状态事件、准备显示、代理发布、Session 回调和无世界回滚都处于同一异常边界；状态监听器或回滚显示失败时直接关闭房间，不留下卡在 `PREPARING` 的对象。

### onPlayerJoin / onPlayerLeave

- 创建/删除 session 内玩家状态。
- 传送玩家并配置初始背包。
- 加入/离开玩法队伍。
- 清理模块私有视觉和实体。

主插件负责完整 PlayerSnapshot，包括位置、生命、吸收生命、生命缩放、经验、背包、装备、额外槽位和末影箱；模块修改的飞行、速度、药水等状态仍建议使用 `PlayerRuntimeStateService`。首次加入或观战前，完整快照会同步写入 `plugins/KaGameCenter/data/player-snapshots/<uuid>.yml`，使用同目录 `.tmp` 和原子移动，因此正常停服、进程异常退出或插件重新加载后仍可在登录时恢复。原世界已卸载或删除时回退首个已加载世界的出生点；快照只在传送和全部 Bukkit 状态成功应用后删除，恢复中途异常、损坏文件或删除失败都会保留正式/临时文件并阻断新房间准入和 Velocity 加入意图，避免覆盖原状态。

### 房间成员与队伍分配事件

`GamePlayerRoomJoinEvent` 在房间准入、容量和准备检查通过后，正式写入玩家或外部观战者身份前触发。事件提供 `room/player/spectator` 并允许取消；取消不会离开玩家当前观战身份，也不会捕获或恢复快照。重复加入已经持有的相同身份直接幂等成功，不重复触发。

`GamePlayerRoomReconnectEvent` 只用于仍在断线宽限内的正式玩家，在重新附加显示和调用玩法重连回调前触发。可空 `respawnDelayTicks` 由玩法预先提供，监听器可修改为非负 tick、`0` 或 `null`；事件通过后核心先应用最终值，再附加显示和恢复玩法。取消不会应用该值，而是结束保留席位、恢复大厅快照，并随后发布原因是 `RECONNECT_REJECTED` 的离开事件；该路径仍视为已处理登录，不继续消费跨服加入意图。BedWars 运行期默认提供 100 tick 并限制最终值不超过 72000，倒计时阶段保持 `null`；原二参数事件构造签名不变。

`GamePlayerRoomAdmissionDeniedEvent` 在目标房间存在、但正式加入、外部观战或宽限重连确定失败后发布，不可取消且不会留下新成员关系。`type` 为 `JOIN/SPECTATE/RECONNECT`，`reason` 为 `ALREADY_ACTIVE/ROOM_NOT_JOINABLE/ROOM_FULL/SPECTATE_NOT_ALLOWED/PREPARATION_FAILED/EVENT_CANCELLED/CALLBACK_FAILED`。最后一项表示观战策略、准入预检事件、基础显示、Session 准入/重连回调或快照事务异常，核心已拒绝或撤销成员、队伍、观战、显示并恢复大厅快照。拒绝通知监听器自身抛异常只记录警告，不改变原准入结果。房间 ID 不存在时没有可归属模块，因此不发布；Velocity 无在线 Player 的远端预留拒绝也不发布。监听器只用于音效、审计或提示，不能在后置事件中递归重试同一次准入。

`GamePlayerRoomLeaveEvent` 在成员和玩法运行状态清理后触发，提供稳定 `playerId`、可空在线 `player`、原身份 `spectator`、可选最近伤害者和离开原因。原因包括 `LEAVE/KICK/DISCONNECT/RECONNECT_EXPIRED/RECONNECT_REJECTED/ROOM_CLOSED/ROLE_CHANGE`；重连超时和关房允许 Player 为空，持久化监听器必须使用 UUID。观战者转正式玩家时顺序为：可取消加入事件、`ROLE_CHANGE` 离开事件、正式身份提交。重连宽限到期时，玩法回调、观战目标、淘汰、队伍、离开事件和显示刷新分别隔离异常；任一步骤失败不会阻止席位释放和持久快照进入待恢复状态。

准入事件与玩法回调的时机不同：`GamePlayerRoomJoinEvent` / `GamePlayerRoomReconnectEvent` 用于提交前取消；`GamePlayerRoomAdmissionDeniedEvent` 只报告最终拒绝；`GameSession.onPlayerJoin`、`onSpectatorJoin` 和 `onPlayerReconnect` 在对应成员关系及基础显示暂存后调用，只有回调正常返回才最终成功。新加入/观战回调抛异常会触发 `CALLBACK_FAILED` 并回滚，不发布未完成提交的离开事件；重连失败则结束原有保留席位，并继续发布 `RECONNECT_REJECTED` 离开事件。成功音效、欢迎提示等反馈应放在后者，并在玩法自己的队伍分配或状态恢复也成功后发送，不能在可取消事件触发时提前宣告成功。

`GamePlayerTeamAssignEvent` 由 `GameTeamService.join` 在目标队伍存在、容量有效后，修改分配前触发，提供 `roomId/player/previousTeamId/teamId`。同队幂等加入不触发，取消后保持原分配并让 `join` 返回 `false`；自动分队可能继续尝试下一个候选队伍。事件没有直接持有 `GameRoom`，监听器可通过公开房间管理器按 `roomId` 查询，且不能在回调中递归调用同一次分配。

### resolveKiller / onPlayerKill / onPlayerDeath

- 主插件收到死亡事件后先调用 `resolveKiller`，再统一记录击杀/死亡统计和触发两个回调。
- 默认实现返回 Bukkit 的 `victim.killer`；需要支持虚空、摔落或延迟爆炸归因的玩法可在 session 内维护短期攻击记录并覆盖该方法。
- 覆盖实现只能返回当前房间内的有效敌方玩家，不能把其他房间或已经失效的实体归为击杀者。
- 击杀者解析、统计、击杀或死亡回调抛异常时，核心停止后续提交并在下一 tick 关闭故障房间；延迟关闭避免在 `PlayerDeathEvent` 尚未完成时向尸体应用大厅快照。
- `canSpectatorFollow` 抛异常时只排除对应候选目标，不中断观战快捷栏事件。

### onStart / onTick

- `onStart` 开始模块内部倒计时或玩法阶段。
- `onTick` 每 tick 调用，必须保持轻量。
- 秒级逻辑使用 `GamePhaseTimer.isSecondBoundary` 或房间定时任务。
- 数据库、文件和 Redis IO 不在 `onTick` 执行。

### onEnd / onClose

- `onEnd` 用于结算开始，可以显示结果和停止玩法输入。
- `onClose` 必须释放任务、实体、视觉、缓存和模块状态。
- `onClose` 后不能继续调度回调访问该 room。

### 整局赛果事件

团队或单胜者玩法通过 `GameResultService.recordWinLoss(...)` 写入全部参赛者胜负后，主插件同步触发不可取消的 `GameResultRecordedEvent`。事件发生在所有统计写入成功之后；单独调用 `recordWin/recordLoss` 不代表完整比赛结束，因此不会触发。

```kotlin
@EventHandler
fun onGameResult(event: GameResultRecordedEvent) {
    if (event.room.module.id != "bedwars") return
    val winnerTeamId = event.winnerGroupId
    // 使用不可变 winners/losers/activeWinners 快照发放外部奖励。
}
```

`participants/winners/losers/activeWinners` 都是保留顺序的不可变 UUID 集合；获胜者会限制在参赛者内，有效获胜者又会限制在获胜者内。`winnerGroupId` 是玩法提供的稳定组 ID，平局或无分组玩法允许为 `null`。事件每次成功调用 `recordWinLoss` 都会触发，模块仍须用 session 内标记保证每局只结算一次；监听器不能取消已持久化的赛果。

BedWars 的 `money-rewards` 通过可选 Vault Economy 发放每分钟、团队支持、胜利、破床、普通击杀和最终击杀金币。胜利与团队支持和 `recordWinLoss` 共用 session 的唯一结算防重，但不写入 KaGameCenter 统计仓库，也不改变 `GameResultRecordedEvent` 的不可变快照。只有在线玩家和成功的 Economy 存款事务收到反馈；服务缺失或事务失败时静默跳过。

### 目标与队伍事件

支持细分目标生命周期的玩法可以在状态提交后触发两个不可取消事件：

- `GameObjectiveDestroyedEvent`：提供 `room/objectiveType/objectiveId/actor/actorTeamId/targetTeamId/sourceId`。
- `GameTeamEliminatedEvent`：提供 `room/teamId`，由玩法保证同一队伍每局只触发一次。

BedWars 破床使用 `objectiveType = "bed"`，并以受害队稳定 ID 同时填充 `objectiveId` 和 `targetTeamId`。玩家手动破坏在床状态、床索引和破床指标更新后触发，`sourceId = "player"`；定时全床销毁和殊死决战兜底销毁在方块全部移除后按仍存活的床逐队触发，`actor` 允许为空，来源分别为 `beds-destroy` 和 `sudden-death`。整队淘汰事件在最后一名有效成员失去参赛资格并登记淘汰队伍后触发，覆盖最终死亡、主动离场和重连宽限到期路径。两者都是观察通知，不能撤销已经提交的状态；需要阻止原始方块破坏时应处理 Bukkit `BlockBreakEvent`。

玩家手动破床还会在上述观察事件之后、默认反馈之前发布 `GameObjectiveDestroyedFeedbackEvent`。`message` 是普通受众消息并控制本次聊天总开关；`targetMessage` 是受害方专属覆盖，为 `null` 时回退普通消息，而 `message=null` 时所有受众均不发送聊天。监听器还可替换或以 `null` 抑制 `targetTitle/targetSubtitle`，但不能撤销床状态、统计、经验或目标事件；BedWars 的敌我音效也不受该显示事件控制。新增属性不改变原 10 参数 JVM 构造器。该事件当前不用于没有破坏者的时间线全床销毁。

### 玩家死亡与复活事件

`GamePlayerFirstSpawnedEvent` 在玩法首次完成正式出生位置和初始装备准备后触发，提供 `room/player/teamId`。BedWars 为开局时在线的参赛者逐人触发；倒计时期间断线并跨过开局时刻的玩家会在重连时补发完整初始装备后触发。session 通过玩家级状态防止普通运行期重连或复活重复触发。

`GamePlayerDeathResolvedEvent` 在玩法完成死亡归因和状态提交后触发，提供 `victimId/victim/victimTeamId`、`killerId/killer/killerTeamId`、Bukkit `damageCause`、模块 `sourceId` 和 `finalDeath`。离线重连超时没有在线受害者，`victim` 为 `null` 但 UUID 保留；击杀者已离线时同理保留 `killerId`。BedWars 召唤物来源使用 `bed-bug` 或 `dream-defender`，运行阶段的重连超时使用 `disconnect`，其他来源允许为 `null`。

在该不可变结果事件之前，支持自定义反馈的玩法可发布 `GamePlayerDeathFeedbackEvent`。上下文与结果事件一致，但额外提供可变的 `message` 和 `playKillerSound`：消息可替换或设为 `null` 抑制，音效可单次关闭。它不允许修改归因或取消死亡；BedWars 会先提交状态、统计和经验，再发布反馈、发送消息/音效，最后发布结果事件。在线普通/最终死亡与运行期断线超时都使用该顺序，倒计时超时不发布死亡反馈。

`GamePlayerRespawnedEvent` 不是 Bukkit 重生事件的别名。支持复活倒计时的玩法只在倒计时结束，并完成玩家位置、装备和保护状态恢复后触发，提供 `room/player/teamId`。BedWars 普通在线倒计时和复活期间重连后完成倒计时共用该入口；最终淘汰者不会触发。

两个事件都不可取消。`finalDeath` 表示该次死亡发生时队伍复活目标已经失效，不等同于“玩家因主动离场或断线被移出本局”；监听器应使用 UUID 作为持久标识，不要长期保存可空 Player 对象。

### 资源等级与主时间线事件

`GameResourceTierChangedEvent` 在玩法提交房间级资源升阶和防重状态后触发，提供 `room/resourceId/previousTier/newTier/scheduledAtSeconds/elapsedSeconds`。BedWars 使用小写 `diamond`、`emerald` 资源 ID，同一资源等级全房间只触发一次，不会按地图上的每个生成点重复发布。

`GameTimelineStageChangedEvent` 在玩法计算出的“下一主事件”发生变化时触发，提供 `previousStageId/nextStageId/elapsedSeconds/nextStageAtSeconds`。BedWars 的稳定 ID 为 `diamond-tier-2/3`、`emerald-tier-2/3`、`beds-destroy`、`sudden-death` 和 `game-end`；进入运行阶段首次确定时 previous 为空，最后事件到点时 next 与截止时间为空。Sidebar 与事件必须调用同一个时间线选择器，不能各自维护排序。

两个事件都不可取消。监听器收到的是已经生效的资源等级和时间线切换，不能回滚内部计时；持久化或网络 IO 应移出同步回调。

## 模块内部阶段

房间 `GameState` 是平台级状态。玩法通常还需要模块内部 phase：

```kotlin
enum class ExamplePhase {
    WAITING,
    COUNTDOWN,
    RUNNING,
    RESULT,
    CLOSING
}
```

phase 必须是 `GameSession` 字段。不要为每个 phase 创建不受追踪的永久任务。

### 房间状态事件

`GameRoom.state` 在值真实变化后同步触发不可取消的 `GameRoomStateChangeEvent`，提供 `room/previousState/newState`。初始 `CREATED` 是对象初值，不算状态变化；重复写入同一状态也不会触发事件。

```kotlin
@EventHandler
fun onRoomStateChange(event: GameRoomStateChangeEvent) {
    if (event.room.module.id != "bedwars") return
    if (event.newState == GameState.RUNNING) {
        // 记录或通知，不在回调中递归改写 room.state。
    }
}
```

监听器收到事件时 `room.state` 已等于 `newState`。事件用于观察生命周期，不提供取消能力；耗时 IO 应移出同步事件。`startRoom` 会先调用模块 `onStart()`，模块可进入 `COUNTDOWN` 或失败状态，只有模块未修改 `WAITING` 时主插件才回退为 `RUNNING`，因此不会产生虚假的 `RUNNING -> COUNTDOWN` 序列。

### 房间准备与关闭事件

`GameRoomPreparedEvent` 只在 `onPrepare()` 成功产出临时世界、房间进入 `WAITING` 且显示和代理状态发布后触发，提供 `room/worldName`。准备失败回退 `CREATED` 时不触发；同一房间后续重复调用 `prepareRoom` 也不会重复触发。`PREPARING/ENDING/CLOSED` 不再被视为已准备成功；Session、显示、代理或准备提交任一步骤抛异常时，核心会关闭该房间并走完整资源回收。

`GameRoomClosedEvent` 在房间已从管理器移除，成员、显示、通用资源和临时世界均完成清理，并写入 `CLOSED` 后触发。事件提供关闭后的 `room`、可空 `worldName` 和 `worldCleanupSucceeded`；没有创建过运行世界时世界名为空且清理结果为成功。两者都不可取消，监听器只能记录、通知或同步外部状态，不能假定关闭事件中的 Bukkit World 仍已加载。

## 玩家身份规则

- 玩家同一时间只能有一个 PlayerSession。
- 重复加入当前房间直接成功，不重复执行离开/加入。
- 重复观战当前房间直接成功。
- 观战者可以在房间允许加入时转换为正式玩家。
- 正式玩家请求观战会被拒绝，必须先正常离开。
- 运行阶段是否允许新玩家加入由房间状态控制。
- 玩家和观战者都为空时房间自动关闭。

## 可选断线重连

`reconnectGraceTicks(player)` 默认返回 `0`，主插件会沿用正常退出流程。需要保留席位的玩法可以返回正数，并在三个回调中维护自己的玩家状态：

- `onPlayerDisconnect`：玩家退出事件中保留房间、队伍和大厅快照，玩法暂停该玩家输入。
- `onPlayerReconnect`：宽限内上线后重新附加显示和名牌，再由玩法恢复位置与阶段。
- `onPlayerReconnectExpired`：宽限到期后先执行玩法淘汰，再由主插件释放队伍和房间席位。

重连期间玩家仍计入房间容量。房间提前关闭或重连超时后，主插件会把大厅快照保留到玩家下次上线恢复。模块私有运行状态仍必须在到期回调或 `onClose` 中清理。

## 事件路由

```kotlin
@EventHandler(ignoreCancelled = true)
fun onDamage(event: EntityDamageByEntityEvent) {
    val player = event.entity as? Player ?: return
    val room = roomManager.getPlayerRoom(player) ?: return
    val session = room.session as? ExampleGameSession ?: return
    if (session.handleDamage(event)) {
        event.isCancelled = true
    }
}
```

Listener 规则：

- 先检查玩家房间。
- 再检查 session 类型。
- 再检查模块 phase 和玩家状态。
- 原版副作用是否取消由 session 返回结果决定。
- 不在 Listener 保存玩法状态。

### 购买扩展事件

支持商店的玩法可以在确认购买资格和余额后、实际扣款前触发 `GamePurchaseEvent`，让其他插件以稳定的主插件类型扩展普通商品或队伍升级。监听器应同时校验 `room.id`、`room.module.id`、`productId` 和 `kind`，不要仅凭商品 ID 处理不同房间或玩法的购买。

```kotlin
@EventHandler
fun onPurchase(event: GamePurchaseEvent) {
    if (event.room.module.id != "bedwars") return
    if (event.kind != GamePurchaseKind.ITEM || event.productId != "custom-item") return

    event.handled = true
    // 在 Bukkit 主线程中执行外部商品行为。
}
```

- 设置 `isCancelled = true` 会终止购买，不扣除货币，也不发送成功反馈。
- 设置 `handled = true` 会保留正常扣款和成功反馈，但跳过模块默认发放或升级行为。
- 事件返回后模块会再次检查并扣除货币，因此监听器修改玩家背包不会造成免费购买。
- 事件字段只使用主插件 API 和 Bukkit 类型；监听器仍须保证主线程安全，避免阻塞事件调用。
- BedWars 商品和升级的 `currency: vault/economy` 使用可选 Vault 账户余额，并在事件中以 `Material.AIR` 保持 `currency` 字段的 Bukkit 类型；缺少服务或扣款失败时购买会安全终止。
- BedWars 商品可附带管理员配置的 `buy-cmds.as-player/as-console`。命令在成功扣款和默认商品发放后执行，支持玩家、UUID、队伍和托管竞技场九项占位符；事件取消时不执行，`handled = true` 时与物品发放一起跳过。玩家命令继续经过局内命令白名单，控制台命令只应放置受信任的固定模板。
- BedWars 商品可用参考 `buy-items` 命名映射或列表在一次扣款后顺序发放多个物品；每个子项独立配置材质、数量、名称、附魔、药水和自动穿戴，商品级永久与不可损坏属性会继承。显式多物品会替代顶层单物品发放，固定装备仍按等级状态在复活时重建。顶层及子项同时兼容 `material/name/enchants` 和模块既有字段名。
- BedWars `POTION` 商品可用 `potion: "SPEED 45 1,JUMP 10 0"` 配置多个效果，并用十进制、`0xRRGGBB` 或 `#RRGGBB` 的 `potion-color` 设置颜色。等级采用 Bukkit 从 0 开始的 amplifier；旧外部配置没有字段时，三个内置药水继续按商品 ID 和模块时长回退。
- BedWars 通用商品的 `auto-equip` 会把实际护甲放入对应槽位；`permanent/is-permanent` 会防止重复购买、写入永久 PDC，并在复活或重连时按商品 ID 重建物品及重放该商品的购买命令。固定护甲、镐斧和剪刀仍走现有等级状态，避免与自定义永久集合重复；购买事件取消或 `handled` 时不登记。
- BedWars 非陷阱升级可在 `receive` 中配置 `command:once-as-console,命令`、`command:foreach-member-as-console,命令` 或 `command:foreach-member-as-player,命令` 动作。购买者和队伍/竞技场 token 先展开，逐成员模式再展开在线有效队员；动作位于升级提交和购买音效后、升级广播前，取消或 `handled` 均不执行。
- 同一 `receive` 列表按顺序支持 `enchant-item`、`player-effect`、`generator-edit` 和 `dragon`。附魔保存到队伍并覆盖现有及后续装备；全队效果在复活时恢复，基地效果按己方基地进出应用；生成器动作精确覆盖间隔、数量和上限并可创建队伍绿宝石点；末影龙动作设置殊死决战队伍龙数。动作仍位于购买音效后和广播前，取消或 `handled` 时全部跳过。
- 陷阱 `receive` 不在购买时执行，而是连同商品身份进入守方队列，敌人进入基地并消费队首时依次执行。支持向敌人/守方全队/基地内守方施加 `player-effect`，从敌人移除 `remove-effect`，以及按剑/护甲/弓执行 `disenchant-item`。存在有效配置动作时替代固定陷阱效果；无有效动作时保留四类内置行为。

### 商店打开事件

支持实体商店的玩法可以在有效玩家点击商店实体、默认界面打开前触发 `GameShopOpenEvent`。事件提供 `room/player/shopId/teamId/shopEntity`，设置取消后玩法不会打开默认菜单；监听器可以先打开自己的界面再取消。BedWars 使用稳定 `item` 和 `upgrade` 商店 ID，只在点击 NPC 时触发，菜单翻页、快捷购买页签和刷新不重复触发。

### 生成器资源拾取事件

`GameResourceCollectEvent` 在有效玩家拾取玩法生成器的地面资源前触发，提供 `room/player/item/itemStack` 并允许取消。取消后底层拾取事件停止，资源实体和房间追踪保持；`itemStack` 每次访问都读取实体当前物品堆。BedWars 只对带生成器标签的独立地面资源触发，身份无效或 AFK 拒绝发生在事件前，队伍分流直接发入背包的资源不触发。

### 商品使用扩展事件

支持持物扩展的玩法可以在确认玩家和交互动作有效后触发 `GameItemUseEvent`。`itemId` 是玩法提供的可选稳定标识；BedWars 会为 `SPECIAL` 商品填入商品 ID，其他物品可能为 `null`，此时监听器可以检查自己写入 `item` 的 PDC。

```kotlin
@EventHandler
fun onItemUse(event: GameItemUseEvent) {
    if (event.room.module.id != "bedwars" || event.itemId != "custom-item") return
    if (event.action != Action.RIGHT_CLICK_AIR && event.action != Action.RIGHT_CLICK_BLOCK) return

    event.handled = true
    // 执行行为、发送反馈，并显式更新对应手的物品数量。
}
```

- 设置 `isCancelled = true` 表示拒绝本次使用，玩法默认行为和原版交互都会停止。
- 设置 `handled = true` 表示外部监听器已经完整接管，同样会停止玩法默认行为和原版交互。
- BedWars 以事件对象身份记录 `cancelled`、`handled` 或默认特殊商品已经接管的 Bukkit 交互，并在 MONITOR 再次确认取消；后续高优先级监听器误解除取消时不会让蛋、雪球、火焰弹等材料同时执行原版行为。未接管的普通交互不受影响。
- `handled` 不会自动消耗物品或发送反馈；监听器必须自行处理，并根据 `hand` 更新正确的背包槽位。
- `action/hand/clickedBlock/clickedFace` 保留本次交互上下文；只应在玩法声明支持该事件时依赖它。

### 投射物、召唤物与自动结构事件

支持玩法实体生命周期扩展的模块可以发布 `GameProjectileLaunchedEvent`、`GameSummonSpawnedEvent` 和 `GameStructureBlockPlacedEvent`。三个事件都提供 `room/sourceId`，并按类型补充玩家、队伍及实际 Bukkit 实体或方块；监听器必须先校验玩法 ID 和房间，不能只按来源 ID 处理。

- `GameProjectileLaunchedEvent` 在投射物完成基础属性配置后、玩法提交物品消耗和默认追踪前触发。取消后玩法移除该投射物，不消耗物品，也不提交对应冷却或生命周期状态；监听器可以在不取消时调整实际 `projectile`。
- `GameSummonSpawnedEvent` 在召唤物完成属性、归属、名称和资源追踪后触发，不可取消。监听器可读取或调整 `entity`，但不能依赖事件撤销已经提交的生成状态。
- `GameStructureBlockPlacedEvent` 在自动结构方块写入世界并纳入房间追踪后逐块触发，不可取消。它可能在同一 tick 高频出现，监听器不得执行阻塞 IO；需要阻止默认特殊商品时应更早取消 `GameItemUseEvent`。
- BedWars 投射物来源为 `fireball/bridge-egg/bed-bug`，召唤物来源为 `bed-bug/dream-defender`，结构来源为 `bridge-egg/pop-up-tower`。

### AFK、基地范围与隐身状态事件

玩法可以在内部状态提交后发布 `GamePlayerAfkStateChangedEvent`、`GamePlayerBaseRegionChangedEvent` 和 `GamePlayerInvisibilityChangedEvent`。三者均不可取消，只用于观察已经发生的状态变化；监听器不应在回调中反向修改 Session 状态。

- AFK 事件提供 `afk/idleSeconds`，进入阈值和恢复活动各发布一次。玩家离房或断线时的生命周期清理不伪造恢复事件。
- 基地范围事件提供 `baseTeamId/entered`。BedWars 使用地图有效 `island-radius` 对所有队伍基地判定，跨基地时先发布旧基地离开、再发布新基地进入，死亡时结束仍登记的基地范围。
- 隐身事件提供 `teamId/invisible`，在玩法完成敌方护甲与名牌隐藏或恢复后触发；自然到期、受伤移除和结算清理都只发布一次恢复状态。

## 开始和关闭

模块通常让房主或管理员调用 `roomManager.startRoom(room.id)`。主插件检查准备状态和最小人数，再调用 `session.onStart()`。回调、房间状态提交、启动显示或代理发布任一步骤抛异常时，核心会关闭该房间并恢复成员，不保留半启动状态；模块主动切换到 `ENDING` 等失败阶段但正常返回时仍由模块自己的结束流程接管。

核心使用一个全局同步任务驱动房间，但每 tick 会先复制活动房间列表，再逐房隔离 `session.onTick()` 与显示刷新。单房间回调异常只关闭故障房间，其他房间继续执行；Velocity 心跳也逐房捕获发布失败，不会让一个损坏快照阻断后续房间或取消周期任务。模块仍不得在 `onTick()` 中执行阻塞 IO。

玩法结束时可以先进入模块 RESULT 阶段，展示完成后调用 `roomManager.closeRoom(room.id)`。关闭会移除房间、恢复玩家、清理观战/队伍/显示/名牌并卸载世界；模块仍负责自己的资源。核心逐项隔离 Session 回调、玩家恢复、通用资源和世界清理异常，前一步失败只记录警告，不阻断后续步骤和最终关闭事件。
